# SDD-001: Paginação nos Endpoints de Listagem

**Status**: `draft`
**Autor**: build
**Criado em**: 2026-07-28

---

## 1. Contexto

O sistema NeonBar atualmente retorna todos os registros nas listagens (produtos, insumos, relatórios) sem paginação. Com o crescimento do catálogo, isso causa:
- Queries lentas retornando milhares de registros
- Alto consumo de memória no frontend
- Timeouts em conexões lentas
- Experiência de usuário degradada (scroll infinito sem controle)

## 2. Objetivos e Não-Objetivos

### Goals
- Adicionar parâmetros `limit`, `offset`, `sort` aos endpoints GET de listagem
- Default `limit=50` para compatibilidade
- Frontend com paginação (IntersectionObserver para scroll infinito + fallback tradicional)
- Zero breaking changes em listas existentes

### Non-Goals
- Cursor-based pagination (mais complexo, não necessário agora)
- Paginação em endpoints de detalhe (GET /{id})
- Cache de paginação (Redis) — fora de escopo MVP

## 3. Arquitetura Proposta

### 3.1 Visão Geral

```
┌─────────────┐     HTTP GET /api/v1/pdv/produtos?limit=50&offset=0&sort=nome:asc
│  Frontend   │ ─────────────────────────────────────────────────────────────────►
│  (React)    │     Response: { data: [...], meta: { total, limit, offset } }
└─────────────┘ ◄─────────────────────────────────────────────────────────────────
       ▲                                                                    │
       │                                                                    ▼
┌─────────────┐     SQL: SELECT * FROM produtos ORDER BY nome LIMIT 50 OFFSET 0
│  Backend    │ ─────────────────────────────────────────────────────────────────►
│  (FastAPI)  │     COUNT(*) OVER() para total
└─────────────┘
```

### 3.2 API Contract

#### Endpoints Afetados

| Endpoint | Método | Parâmetros Novos |
|----------|--------|------------------|
| `/api/v1/pdv/produtos` | GET | `limit`, `offset`, `sort` |
| `/api/v1/estoque/insumos` | GET | `limit`, `offset`, `sort` |
| `/api/v1/relatorios/auditoria` | GET | `limit`, `offset`, `sort` |
| `/api/v1/relatorios/movimentacoes` | GET | `limit`, `offset`, `sort` |
| `/api/v1/produto-lotes/` | GET | `limit`, `offset`, `sort` |
| `/api/v1/lotes/` | GET | `limit`, `offset`, `sort` |
| `/api/v1/etiquetas/` | GET | `limit`, `offset`, `sort` |
| `/api/v1/fichas-tecnicas/` | GET | `limit`, `offset`, `sort` |

#### Parâmetros de Query

| Parâmetro | Tipo | Default | Descrição |
|-----------|------|---------|-----------|
| `limit` | int | 50 | Máximo de itens por página (1-100) |
| `offset` | int | 0 | Número de itens a pular |
| `sort` | string | `nome:asc` | Campo e direção: `campo:asc` ou `campo:desc` |

#### Response Format (Novo)

```json
{
  "data": [...],
  "meta": {
    "total": 150,
    "limit": 50,
    "offset": 0,
    "has_more": true
  }
}
```

**Compatibilidade**: Endpoints existentes continuam funcionando — se `limit`/`offset` não enviados, usa defaults e retorna formato antigo (array direto) OU novo formato com meta. **Decisão**: Retornar **sempre** o novo formato com `meta` para consistência. Frontend antigo ignora `meta`.

### 3.3 Data Model

Nenhuma mudança no banco de dados. Apenas queries SQL com `LIMIT`/`OFFSET` e `COUNT(*) OVER()` para total.

### 3.4 Fluxo de Dados

1. Frontend faz request com `limit=50&offset=0&sort=nome:asc`
2. Backend valida parâmetros (limit ≤ 100, offset ≥ 0)
3. Backend executa query paginada + count total
4. Backend retorna `{ data, meta }`
5. Frontend renderiza lista + mostra "carregar mais" se `has_more`

## 4. Alternativas Consideradas

| Alternativa | Prós | Contras | Decisão |
|-------------|------|---------|---------|
| Offset/limit (escolhida) | Simples, padrão REST, funciona com qualquer ordenação | Offset lento em tabelas grandes (>100k) | ✅ Aceito — catálogo < 10k itens |
| Cursor-based | Performático em grandes datasets | Complexo, não funciona com sort arbitrário | ❌ Rejeitado — overkill |
| Page/size | Mais intuitivo para usuários | Menos flexível que offset/limit | ❌ Rejeitado — offset/limit é padrão da API |

## 5. Segurança

- Validar `limit` (max 100) para evitar DoS via queries gigantes
- Validar `offset` (≥ 0)
- Sanitizar `sort` — apenas campos permitidos (whitelist) para evitar SQL injection via ORDER BY
- Rate limiting já existe no middleware global
